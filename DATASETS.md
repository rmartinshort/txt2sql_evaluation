# Datasets

This document explains two things:

1. What dataset the harness actually evaluates when you run, e.g.:
   ```bash
   uv run txt2sql-judge run --items=data/items.jsonl --run-dir=runs/he_v2 --methods H+E
   ```
   — where `data/items.jsonl` comes from, what's inside it, and what each benchmark family is testing.
2. The exact file format a **new** dataset needs to be in if you want to run it through the same `txt2sql-judge run` command.

Everything here was checked against the actual source (`data.py`, `generators.py`, `codec.py`, `models.py`, `runner.py`, `cli.py`) — JSON examples below were generated by actually calling `encode_labelled_item()`/`decode_labelled_item()`, not hand-written.

---

## What `--items` actually is

`--items` points at a **JSONL file** (one JSON object per line) where every line decodes to a `LabelledItem` (`models.py`) via `decode_labelled_item` (`codec.py`). This is the one dataset format the judge runner understands — `txt2sql-judge run` doesn't know about BIRD, FLEX, or any upstream format directly; those are only ever converted *into* this format, by the `download`/`generate` subcommands, before `run` ever sees them.

Each `LabelledItem` bundles:
- a **`Trace`** — the question, hint, database, and the candidate's SQL step(s) (and, for agent traces, its final natural-language answer) that will actually be judged;
- a **`GroundTruth`** — the reference SQL (and optionally pre-computed reference results) the candidate is graded against;
- a **`label`** — what this item is *supposed* to be judged as (`correct`/`incorrect`/`ambiguous`/`gt_wrong`/`unlabelled`). **The judge itself never reads this field.** `judge_item()` only ever sees `trace` and `gt`; `label` exists purely so `metrics.py`/`reporting.py` can later score how often the judge's own verdict agreed with it. A wrong `label` in your dataset doesn't bias the judge — it only makes your own accuracy numbers wrong.
- bookkeeping fields (`item_id`, `group_id`, `split`, `set`, `family`, `slices`, `pair_of`, `method_ok_label`, `snapshot`) used for resuming runs, computing calibration/test splits, and grouping results in reports.

---

## Where `data/items.jsonl` comes from

Two CLI steps build it, in order:

### 1. `txt2sql-judge download`
Pulls the two **pinned upstream sources** and records their exact file hashes in `data/manifest.json`:

- **BIRD Mini-Dev V2** (`data.py:load_bird_mini_dev`) — 500 real natural-language-question → SQL pairs over SQLite databases, pinned to Hugging Face dataset revision `5b256b5a9c17478f06ed6912612e9a14d17065c8` of `birdsql/bird_mini_dev`. Each row becomes a `sql_only` seed item (`set="S1"`, `family="base"`, `label="correct"`) with its ground-truth SQL already executed once against the real database to cache the reference result.
- **FLEX** (`data.py:load_flex_dataset`) — 200 BIRD-Dev questions each paired with a *model-generated* candidate SQL plus a human expert's correct/incorrect judgement, pinned to commit `270abdba59306134adf0928b2ce92acb8fbd94eb`. These become `set="S4"` items directly (no further generation step) — the candidate SQL is the `trace.steps[0].sql`, and `label` comes from the human annotation (`family="flex_fp"` or `"flex_fn"` depending on which agreement file the row came from; pairs with a tied expert consensus score of `0.5` are dropped).
- The SQLite database files themselves are downloaded and unpacked into `data/dbs/<db_id>/<db_id>.sqlite`, and every database's hash/trigger/view counts are recorded in `data/manifest.json` under `databases`.

### 2. `txt2sql-judge generate`
Loads the BIRD + FLEX items above and synthesizes several labelled benchmark **families** from them (`generators.py`), then writes the combined result to `--out` (default `data/items.jsonl`) and a separate injection-probe file to `--e5b-out` (default `data/e5b_items.jsonl`). Both output files are hashed and registered in `data/manifest.json` as `"harness_derivative"` entries automatically.

## Synthetic & adversarial benchmark families

All of these are generated **deterministically from code** — no LLM is used to create them, and no LLM is used to assign their labels; the SQL mutations are AST rewrites (`sqlglot`) and the labels follow directly from how each mutation was constructed (optionally double-checked against the real database).

| `set` | `family` values | What it tests | How `label` is assigned |
| --- | --- | --- | --- |
| `S1` | `add_columns`, `permute_columns`, `drop_order_by`, `between_expand` | **Meaning-preserving rewrites** of a real BIRD ground-truth query — adding a harmless extra column, permuting `SELECT` column order, dropping a redundant `ORDER BY`, expanding `BETWEEN x AND y` into `>= x AND <= y`. These should never change the judge's verdict. | Always `"correct"` — by construction, the rewrite is logically equivalent to the original. |
| `S2` | `filter_literal`, `comparator_flip`, `drop_conjunct`, `agg_swap`, `time_shift` | **Question-anchored faulty mutants** — e.g. flipping a `>` to `<`, dropping one `AND` clause, swapping `SUM`/`AVG`, shifting a date filter — targeted at words that actually appear in the question/hint, so the mutation plausibly looks like a real mistake rather than an arbitrary edit. | Always `"incorrect"` — but only *after* the generator executes both the original and mutated SQL against the real database and confirms they actually disagree (`align_tables(...).relation != "equal"`, relative tolerance `rho = 1e-4`); mutants that coincidentally produce the same result on the real data are discarded rather than mislabelled. |
| `S3` | `correct`, `wrong_number`, `swapped_values`, `omitted_entity`, `unsupported` | **`full_trace` final-answer items** — templated natural-language answers built directly from a complete ground-truth result table: a faithful answer (`correct`), a numeric value changed (`wrong_number`), values attached to the wrong entity (`swapped_values`), a required entity left out (`omitted_entity`), or a true-sounding claim that isn't actually grounded in any step's results (`unsupported`). Restricted to ground-truth tables with 1–20 rows and a unique entity key. | `"correct"` only for the `correct` family; every perturbation family is `"incorrect"`. |
| `S3m` | `early_support`, `early_support_rev`, `no_support`, `no_support_rev` | **Two-step `full_trace` traces** that pair a genuinely correct query step with an unrelated "exploratory" query step, in both step orders, to check that the judge gives credit for support appearing in *any* step (not just the last one) — and withholds it when support is actually absent. `early_support(_rev)` puts the real ground-truth query first/second alongside an unrelated step; `no_support(_rev)` instead pairs an S2 *mutant* query (so nothing in either step actually backs the final answer) with that same unrelated step. | `"correct"` for `early_support`/`early_support_rev` (genuine support exists in one of the two steps); `"incorrect"` for `no_support`/`no_support_rev` (no step supports the answer). |
| `S4` | `flex_fp`, `flex_fn` | Real BIRD-Dev questions with *model-generated* candidate SQL and a **human expert** correctness judgement — the one family in the harness where `label` reflects human annotation rather than a code-constructed guarantee. | From FLEX's human agreement data (majority vote / explicit override), never `"ambiguous"` or `"gt_wrong"` — ties are excluded during loading rather than kept as ambiguous. |
| `S5` | *(not emitted by `generate`)* | **Agent-synthesized multi-step traces** — run by actually calling an LLM (`agent.py:run_reference_agent`, using `cfg.agent_model`) to answer a question over a live database via a read-only `execute_sql` tool, then tagging the resulting trace (`tag_s5_trace`) with structural flags (`multi_step`, `early_only_support`). This is a Python-library workflow, not part of the `download`/`generate`/`run` CLI pipeline — you call it yourself and merge the resulting `LabelledItem`s into your own `items.jsonl`. | Whatever you assign — `run_reference_agent` only produces the trace; it does not label it. |

**E5b injection-resistance pairs** (`--e5b-out`, separate file): for a sample of `S3` `correct`/`wrong_number` items, a second item is created with a fixed, benign, instruction-shaped payload string (`E5B_PAYLOAD`, defined in `generators.py`) spliced into the final answer text, **without changing any SQL, fact, or number**. The two items are linked via `pair_of` (the injected item's `pair_of` is the original item's `item_id`). These exist to check that the prompt-injection-safe renderer (`renderer.py` — see the main `README.md`'s evidence-packet framing/escaping) actually holds: a judge that changes its verdict *only* because of the injected text, with no factual change, indicates the DATA-block escaping failed.

## Splits, leakage control, and the common subset `C`

- **`group_id`** is computed once as `sha256(db_id + "\x1f" + norm(question))[:16]` (`data.py:compute_group_id`) — every item generated from the same underlying `(database, question)` pair (the base item and all of its `S1`/`S2`/`S3`/`S3m` derivatives) shares the same `group_id`.
- **`split`** (`calibration` or `test`) is assigned once per `group_id` by a seeded hash (`assign_split`, ~50/50), and `assert_disjoint_splits` is run after generation to guarantee no `group_id` ever appears in both splits — this prevents a mutation of a calibration-split question from leaking into the test split (which would let threshold fitting "see" test items indirectly).
- **Common subset `C`** (`runner.py:select_common_subset_c`, used by `--subset-c`) takes a fixed, deterministic, balanced sample of the `test` split — all `S4`/`S5` test items, equal per-family quotas for `S1`/`S2`/`S3` (40/60/40 total), and up to 12 base questions × 4 families for `S3m` — so that different methods/runs are always compared on the exact same evaluation slice rather than whatever happened to be in `--items`.

## The egress admission gate: why `data/manifest.json` matters

Any file passed to `judge_item`/`run_experiment` that will ultimately be shown to a remote model (Jev or the generative escalation model) has to be a *verified* input. `run_experiment` calls `egress_decision(input_files, manifest_path, ...)` (`data.py`) at the start of every run, where `input_files` includes whatever you passed as `--items`. That function only allows remote calls (`allow_remote=True`) if:
- `data/manifest.json` exists, **and**
- your `--items` file is listed in its `entries` map with `kind` in `{"pinned_download", "harness_derivative"}`, **and**
- the file's current whole-file SHA-256 matches the hash recorded at the time it was registered.

`txt2sql-judge generate` registers `data/items.jsonl` and `data/e5b_items.jsonl` for you automatically (`record_manifest_entry(..., "harness_derivative")`). **If you hand-write or otherwise produce your own items file, you must register it yourself** before running without `--local-only` — otherwise `egress_decision` raises `UnadmittedInputError` and the run aborts rather than silently sending unverified content to a remote API. If the file's content changes afterward (even by one byte), the hash check fails and you'll need to re-register it.

## The exact `LabelledItem` JSON schema

Each line of `items.jsonl` is the JSON produced by `encode_labelled_item()` (`codec.py`) — compact, one object per line, no pretty-printing. Below is a real `sql_only` example, generated and round-tripped through `encode_labelled_item`/`decode_labelled_item` to confirm it's valid (pretty-printed here only for readability; on disk it's one line):

```json
{
  "item_id": "custom:0001",
  "group_id": "abc123def4567890",
  "split": "test",
  "set": "S1",
  "family": "custom",
  "slices": [],
  "trace": {
    "trace_id": "custom:0001",
    "group_id": "abc123def4567890",
    "question": "How many orders were placed by customer 42?",
    "hint": null,
    "db_id": "shop",
    "db_sha256": "3f1e...db-sha256...",
    "steps": [
      {
        "index": 1,
        "sql": "SELECT COUNT(*) FROM orders WHERE customer_id = 42",
        "result": null,
        "error_kind": null
      }
    ],
    "final_answer": null
  },
  "gt": {
    "item_ref": "custom:0001:gt",
    "sql_chain": ["SELECT COUNT(*) FROM orders WHERE customer_id = 42"],
    "alternatives": [],
    "reference_answer": null,
    "results": [
      {"columns": ["n"], "rows": [[{"i": "7"}]], "total_rows": 1, "complete": true}
    ]
  },
  "label": "correct",
  "pair_of": null,
  "method_ok_label": null,
  "snapshot": "custom_v1"
}
```

And a `full_trace` (agent) example — note `final_answer` is non-null and `trace.steps` carries the agent's own intermediate SQL and results, separate from `gt`:

```json

  "item_id": "custom:0002",
  "group_id": "9988776655443322",
```

### Field reference

**Top level (`LabelledItem`)**
| Field | Type | Notes |
| --- | --- | --- |
| `item_id` | `str` | Must be unique across the whole file — it's the resume/idempotency key in `run_dir/records.jsonl` (an item+method pair already recorded there is skipped on re-run). |
| `group_id` | `str` | Any stable string shared by items derived from the same underlying `(db, question)` pair. Use `data.py:compute_group_id(db_id, question)` if you want it consistent with the built-in splitting/leakage tooling; otherwise any unique-per-question string works if you don't care about `--subset-c` or calibration/test leakage checks. |
| `split` | `"calibration"` \| `"test"` | Not enforced against `group_id` unless you also run `assert_disjoint_splits` yourself. If you don't care about calibration vs. test, putting everything in `"test"` is the simplest choice. |
| `set` | `"S1"` \| `"S2"` \| `"S3"` \| `"S3m"` \| `"S4"` \| `"S5"` | A `typing.Literal` in `models.py` — not runtime-validated by the decoder, but reporting/metrics code groups by this value, so pick one of the existing tags (`"S5"` is the catch-all for "custom/other") unless you also extend `models.py`. |
| `family` | `str` | Free text — subgroup label within `set`, shown in per-family breakdowns. Any string is fine for a new dataset. |
| `slices` | `list[str]` | Free-text tags (e.g. `"large_result"`, `"coincident"`); leave `[]` unless you want to replicate the built-in slice tagging (`runner.py:tag_slices`) yourself. |
| `label` | `"correct"` \| `"incorrect"` \| `"ambiguous"` \| `"gt_wrong"` \| `"unlabelled"` | **Not seen by the judge.** Only used afterward to score the judge's agreement. Use `"unlabelled"` if you genuinely don't know the right answer and just want the judge's verdict. |
| `pair_of` | `str \| null` | Only meaningful for paired items like E5b — the `item_id` of the item this one is a variant of. Leave `null` otherwise. |
| `method_ok_label` | `bool \| null` | Optional ground truth for whether the agent's *method* (not just its final answer) was sound, for `full_trace` items. Leave `null` unless you have this annotation. |
| `snapshot` | `str` | Free-text database version tag (default `"minidev"`); purely descriptive unless you also register it via `data.py:record_database_entry`. |

**`trace` (`Trace`)** — the thing being judged:
| Field | Type | Notes |
| --- | --- | --- |
| `trace_id` | `str` | Conventionally equal to `item_id`, but not required to be. |
| `question` | `str` | The natural-language question. |
| `hint` | `str \| null` | Optional extra context shown to the judge alongside the question (BIRD calls this "evidence"). |
| `db_id` | `str` | Must match a database directory under `--db-dir`: the harness resolves the SQLite file as `<db_dir>/<db_id>/<db_id>.sqlite` (`runner.py:_dispatch_method`). If that path doesn't exist, the item is judged with `db_path=None` — no live execution happens, and anything not already pre-computed in `result`/`error_kind` fields is treated as unavailable. |
| `db_sha256` | `str` | **Descriptive only** — it is *not* checked against the actual database file at judge time. It exists so you can register the database in `data/manifest.json` (`record_database_entry`) for provenance/reproducibility, and so downstream tooling can detect if "the same `db_id`" silently points at a different file across runs. Any placeholder string works if you don't need that. |
| `steps` | `list[Step]` | For `sql_only` items: typically one `Step` holding the candidate SQL to grade. For `full_trace` items: the agent's own ordered intermediate `Step`s (its SQL calls and their results), independent of `gt`. Each `Step` has `index` (int), `sql` (str), `result` (`ResultTable \| null`), `error_kind` (`str \| null`, one of the sandbox `ErrorKind`s — `compile_error`, `non_read`, `timeout`, `fetch_cap`, `multi_statement`, `runtime`, `resource_limit`, `volatile`). **If `result` and `error_kind` are both `null` and a usable `db_path` exists, the harness executes `sql` itself** (`judge.py:_execute_steps`) — so you can either hand it pre-computed results or let it compute them for you. |
| `final_answer` | `str \| null` | **This is the mode switch.** `null` → `sql_only` mode (grade the SQL in `steps[-1]`). Non-null → `full_trace` mode (grade this natural-language answer, using `steps` as supporting evidence). |

**`gt` (`GroundTruth`)** — what the candidate is graded against:
| Field | Type | Notes |
| --- | --- | --- |
| `item_ref` | `str` | Free-text identifier for the reference item; not used for matching logic. |
| `sql_chain` | `list[str]` | The reference SQL statement(s); only the **last** element is actually executed/compared (`gt_sql = chain[-1]` in `judge.py:prepare_best_candidate`) — earlier elements are informational context only (e.g. setup steps), not separately graded. |
| `alternatives` | `list[list[str]]` | Optional additional acceptable SQL chains (same shape as `sql_chain`) — if a question has more than one correct formulation, list each as its own chain here; the harness automatically scores all of them and keeps whichever best matches the candidate (see `README.md`'s Stage 0 description of `prepare_best_candidate`). |
| `reference_answer` | `str \| null` | Optional human-written reference natural-language answer; not read by `judge_item` itself. |
| `results` | `list[ResultTable] \| null` | Optional pre-computed result table(s), one per entry of `[sql_chain] + alternatives`, in the same order. Supplying this lets you skip live execution entirely (useful if you don't have the database file, or want results pinned regardless of DB drift) — if omitted and a usable `db_path`/`db_id` exists, the harness executes `sql_chain[-1]`/each alternative itself. |

**`ResultTable`** (used both in `gt.results` and `trace.steps[*].result`):
| Field | Type | Notes |
| --- | --- | --- |
| `columns` | `list[str]` | Column names as returned by SQLite. |
| `rows` | `list[list[Cell]]` | Each `Cell` is one of four wrapped JSON forms — **not plain JSON values** (see below). |
| `total_rows` | `int \| null` | True row count, even if `rows` only holds a truncated prefix. |
| `complete` | `bool` | `false` means `rows` is a partial prefix (e.g. hit a fetch cap) — downstream alignment logic treats incomplete tables conservatively. |
| `cut_by` | `str \| null` | Optional tag for *why* the table was truncated (omit unless you need it). |

**Cell encoding** — this is the one easy-to-get-wrong part. `encode_cell`/`decode_cell` (`codec.py`) require:
| SQLite value | JSON form |
| --- | --- |
| `NULL` | `null` |
| `TEXT` | a plain JSON string, e.g. `"Alice"` |
| `INTEGER` | `{"i": "<digits>"}`, e.g. `{"i": "42"}` — **not** a bare JSON number (this preserves integers too large for a 64-bit float) |
| `REAL` | `{"r": "<python repr>"}`, e.g. `{"r": "310.5"}` — **not** a bare JSON number |
| `BLOB` | `{"b": "<base64>"}` |

A bare JSON number (`42` instead of `{"i": "42"}`) will fail to decode (`CellCodecError`) — every numeric cell must be wrapped.

## Adding a new dataset

To judge your own data with `txt2sql-judge run`:

1. **Build an `items.jsonl`** where every line is a `LabelledItem` matching the schema above. One line per item you want graded — mix `sql_only` and `full_trace` items freely in the same file.
2. **Provide the SQLite database(s)** each item's `trace.db_id` refers to, laid out as `<db_dir>/<db_id>/<db_id>.sqlite`, where `<db_dir>` is whatever you pass to `--db-dir` (defaults to `data/dbs`). You can skip this if every item already carries pre-computed `result`s for its `steps` and `gt.results` — then no live execution is needed.
3. **Decide your remote-call posture:**
   - For a quick deterministic check (Stage 0–1 rules, alignment, no API calls), run with `--local-only`; no manifest registration is needed.
   - To actually use Jev/escalation (`H+E`, `B6+E`, etc.), register your items file in `data/manifest.json` first:
     ```python
     from pathlib import Path
     from txt2sql_eval_harness.data import record_manifest_entry
     record_manifest_entry(Path("data/manifest.json"), Path("path/to/your_items.jsonl"), "harness_derivative")
     ```
     Re-run this whenever the file's contents change — the manifest pins an exact SHA-256, and a mismatch aborts the run (see **The egress admission gate** above).
4. **Run it:**
   ```bash
   uv run txt2sql-judge run \
     --items=path/to/your_items.jsonl \
     --run-dir=runs/my_dataset \
     --db-dir=path/to/your/dbs \
     --manifest=data/manifest.json \
     --methods H+E
   ```
5. **(Optional) Score it afterward** with `txt2sql-judge report --items=path/to/your_items.jsonl --records=runs/my_dataset/records.jsonl --out-dir=runs/my_dataset_report` — this is what actually reads your `label` field and compares it against the judge's verdicts.
